# 抖音数据获取：社区口径与技术手段调研

调研日期：2026-09-11。目的：为「抖音能否不走「必须在主页渲染」这条路」提供依据。
所有结论标注来源，推断部分明确标为推断。

---

## 一、结论先行

1. **官方路径拿不到「追踪任意创作者」这件事。** 开放平台的 `video.list` / `video.data`
   只能读**当前授权用户本人**的作品；要看别人的作品，需要**那个人单独授权**。
   所以本项目的核心用法（关注一群创作者、只读公开内容）**没有官方 API 解法**。
2. **社区主流不做 DOM 抓取，而是「浏览器产身份 + 签名算法 + 调接口」。** 但这套东西
   **需要持续维护**，且维护者本人承认「接口会悄悄死掉，而你不知道」。
3. **社区一致推荐「连接你自己真实的浏览器」** —— 这一点我们的架构天然满足，
   是已知最抗风控的形态。
4. **`window._ROUTER_DATA` 内嵌数据**是社区经典手段，但依赖**分享页**，
   该路径历史上被反复打断，且**当前主要靠它的工具都已失效或需登录 Cookie**。
5. **隐藏作品确实计入主页作品数** —— 已由用户确认，社区资料亦支持。
   这使「与标注数比对」无法用来判断网格是否完整。

## 二、官方口径（合规路径）

| 能力 | 限制 |
|---|---|
| `video.list`（作品列表） | 只返回**授权用户本人**的作品 |
| `video.data`（作品数据） | 同上；**未公开的作品不返回**，设为隐私的返回 `create_time = 0` |
| 授权要求 | 数据经营类能力（`video.list`/`video.data`/`fans.data`）**必须 PC 端完成授权** |

来源：抖音开放平台《能力概览》《用户类型及权限说明》《总体授权说明》，
以及 2023-06-12 起的「网站应用获取用户授权方式调整」公告。

**要点**：平台**不提供**「用单一 scope 查询任意他人作品列表」的能力。
这是设计取向（避免 C 端用户在无预期下把敏感权限交出去），不是技术空缺。

→ 对本项目的意义：**没有任何官方路径可以合法批量追踪他人创作者**。
这一点必须如实呈现在文档与上架说明里，而不是含糊带过。

## 三、技术手段（社区实际做法）

### 3.1 签名参数：a_bogus / X-Bogus / __signature

Web 接口的防爬校验依赖三类签名：

| 参数 | 机制 |
|---|---|
| `a_bogus` | 路径 + 查询串 + 时间戳 + UA 拼接后 SM3 哈希，再交给**混淆的 JS VM**，输出 Base64URL 串 |
| `X-Bogus` | `a_bogus` 的升级版：额外加 CRC32、加盐、自定义字符映射，并**自动注入 `msToken`、`ttwid`** |
| `__signature` | 来自字节 `webmssdk`，用 RSA-PKCS1-v1_5 对同样拼装串签名，配合 `x_ms_stub` |

社区已有开源实现（`xbogus.py` / `xbogus.js`，以及纯 Python 版），
但**算法会变**：`a_bogus` 2025 年的实现被固定在 `V1.0.1.19-fix.01`，需要跟着更新。

**这为什么与本项目冲突（关键）**：
跑通签名需要 `ttwid`、`msToken`、以及**页面自己生成的签名状态**。
而本项目有一条硬约束（AGENTS 规则 9）——抖音采集层**只读渲染后的 DOM，
不读 `document.cookie`、`localStorage`、请求头或设备/签名状态**。

这不是洁癖。一旦开始搬运签名与设备标识，这个扩展在技术定义上就变成
「持有用户凭据的自动化代理」，其**权限模型、上架说明与隐私政策全部要重写**。
**结论：签名路线与项目定位不相容，明确排除。**

来源：`ylcangel/a_bogus`、掘金/博客园参数说明、B 站逆向课程、CSDN 分析文章。

### 3.2 `window._ROUTER_DATA` 内嵌 JSON

社区经典手段：请求**分享页**，正则提取内嵌 JSON：

```
GET https://www.iesdouyin.com/share/user/<sec_uid>
→ window._ROUTER_DATA = { loaderData: { "user_(id)/page": ... } }
```

**优点**：服务端渲染，**不需要执行 JS、不需要渲染网格** —— 正好绕开我们的核心痛点。

**风险**（都有来源）：
- 该路径**历史上被反复打断**：2020-06 加 `sec_uid`、2020-09 再改、之后又变；
- 目前它**依赖动态签名与已登录 Cookie**，旧脚本生成的参数拿不到数据，常见返回 403 或空；
- 仍在维护的工具（如 `Douyin_TikTok_Download_API`）能取到数据的前提是
  **提供已登录账号的 Cookie 并持续更新签名算法**。

**待验证的推断**：`_ROUTER_DATA` **可能**也存在于 `www.douyin.com/user/<sec_uid>`
的 HTML 里。若存在，则在**真实浏览器会话内**读取它，既不违反规则 9（它不是 cookie、
不是设备状态，是页面自己的数据），又不依赖网格绘制 —— 探针与「网格未渲染」整类问题
会消失。

**这仍只是推断，未经实测。** 验证方法见 §五。

### 3.3 浏览器自动化抓取（与我们最接近）

社区对 Selenium/Playwright 的共识：
- **技术上可行，但必须反检测**：隐藏 `navigator.webdriver`、去 `--enable-automation`、
  stealth 脚本等；即便这样，**行为分析、请求频率、异常网络特征仍会二次检测**，
  滑块 / 人机验证 / IP 封禁的风险始终存在。
- 抖音**能识别**加了 stealth 的 WebKit/Firefox；加 stealth 的 Chromium 较难被识别。

**最关键的一条**（来自 MediaCrawler 的官方问答）：

> 强烈建议使用 **CDP 模式连接自己的真实浏览器**（默认配置），
> 不要使用无痕浏览器或标准 Playwright 模式。
> **连接真实浏览器可以复用已有的 Cookie、登录状态和浏览历史，大幅降低被风控检测的概率。**

**这正是本扩展的形态** —— 它运行在用户真实浏览器内、用真实会话、真实 profile。
所以我们的**架构是社区推荐的那一端**，不是需要伪装的那一端。

**我们唯一缺的是「渲染」**，而那是**浏览器行为**、不是反爬：
后台（隐藏）标签页不绘制。这解释了为什么「复用用户已打开的抖音页」总是成功。

来源：`NanmiCoder/MediaCrawler` 常见问题、CSDN/掘金 Playwright 反检测、知乎反爬工具链综述。

### 3.4 主流开源项目现状

| 项目 | 状态 | 手段 |
|---|---|---|
| `Evil0ctal/Douyin_TikTok_Download_API`（~20k★） | 🟡 活着，复杂度高 | v5：**无头浏览器铸造游客身份池** + 纯 Python 签名（a_bogus / X-Bogus / X-Gnarly / X-Dynosaur）+ **浏览器 TLS 指纹模拟**（`wreq`）+ 令牌桶/熔断 |
| 多数 2025-2026 列出的爬虫 | ⚫ 已失效 / 「有风险」 | — |

该项目 README 的自述值得引用：

> v4 最大的问题从来不是功能少，而是**接口会悄悄死掉，而你不知道**。
> Cookie 过期、签名算法变更、某个接口被风控，通常都要等到有人来提 issue 才发现。

以及它的免责声明（可视为社区对**合规边界**的共识）：

> 本项目从有自己服务条款的平台抓取数据，并且运行在你自己控制的机器上。
> 请遵守平台条款和所在地法律，尊重你所收集内容背后的人，
> 不要拿它去骚扰任何人，也不要拿它去二次分发不属于你的作品。

**注意**：它 v5 用**无头浏览器铸身份**，我们用的是**用户的真实浏览器**。
从这个角度看，**我们的侵入性更低**：不伪造身份、不模拟 TLS 指纹、不维护身份池。

## 四、对本项目的三条实际结论

1. **官方路径不存在**，必须如实说明：
   「本扩展通过读取你在自己浏览器中已打开/可访问的公开页面来聚合内容，
   不破解平台接口、不伪造身份。」
2. **签名路线排除**（与规则 9 及上架定位不相容）。这条要写进代码注释，
   防止后人「顺手」加上。
3. **社区最推荐的真实浏览器形态，我们已经在用。** 剩下的唯一技术缺口是
   **后台标签页不渲染**，而那是浏览器渲染行为，不是反爬 —— 有两种可能解法
   （见下），都不涉及签名或身份伪造。

## 五、下一步的验证计划（待用户配合）

**假设 H1**：`www.douyin.com/user/<sec_uid>` 的 HTML 内嵌了作品数据
（`_ROUTER_DATA` 或某个 `<script type="application/json">`），
可在**不依赖网格绘制**的情况下读取。

**验证方式**（只读，不导航、不关标签页，事后向用户报告读到了什么字段名）：
在用户已打开的抖音创作者页面上注入一小段只读探针，报告：
- `window._ROUTER_DATA` 是否存在、顶层键名
- 是否存在 `<script type="application/json">`
- 若存在，报告其**键名路径**（不回报内容）

**若 H1 成立**：采集改为「读内嵌数据优先，DOM 兜底」，
后台标签页问题、探针超时问题、`Frame with ID 0 was removed` 整类问题一并消失。

**若 H1 不成立**：剩两条路 —— 让临时页短暂激活（会抢焦点），
或接受「需用户先打开该创作者页面」的既有约束并把它做成明确的 UX 提示。

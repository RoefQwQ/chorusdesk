# Chorus security and quality review — 2026-09

> **历史记录（不与当前代码同步）**：本文记录 2026-09 阶段当时的结论与状态。
> 当前实现以源码与 [架构设计说明](ARCHITECTURE.md) 为准；两者冲突时以后者为准。
> 本阶段的持续记录见 [项目进度](PROJECT_PROGRESS_2026-09.md)。

## Status

The review covered Chrome MV3 lifecycle behavior, privileged messaging, credential handling,
IndexedDB correctness, adapter data integrity, backup restore, query performance, UI accessibility,
and CI coverage.

All 12 remediation items are complete. Reusable engineering constraints live in `AGENTS.md`; this
file intentionally records outcomes rather than historical exploit details or internal investigation
notes.

## Security outcomes

- Platform identity is determined from a parsed HTTP(S) URL and hostname, never from a substring.
- `PLATFORM_HOSTS` is the single credential allowlist. Arbitrary RSS URLs remain reachable, but do
  not receive browser credentials.
- Privileged runtime messages are governed by a central sender-policy table. Unknown message types
  are denied by default.
- Background fetch is GET-only; callers cannot select credential policy.
- DNR header and scheme rules are restricted to requests initiated by this extension and no longer
  apply to subframes.
- Embedded URL credentials and non-HTTP(S) schemes are rejected.
- No remote code, telemetry, analytics, relaxed CSP, `<all_urls>`, or web-accessible resources were
  found.

## Correctness outcomes

- Indexed `isRead` and `isBookmarked` fields are persisted as `0 | 1`, including a Dexie migration
  for posts and recycle-bin snapshots.
- Service-worker synchronization calls the background fetch implementation directly rather than
  messaging its own context.
- Alarm setup no longer resets an existing periodic alarm during normal service-worker startup.
- Adapter post identities are stable; items without a reliable identity are skipped instead of
  receiving random IDs.
- Parsed timestamps are checked for finite values before persistence and indexing.
- RSS identifiers support Unicode through a UTF-8 deterministic hash.
- Backup restore validates the format version, section shapes, and required record identity fields
  before any database write.
- Adapter failures use structured `FetchError` values; synchronization decisions no longer depend
  on localized message text.
- Unsupported platforms are reported explicitly instead of falling back to another adapter.

## Performance and architecture outcomes

- Watermark lookup uses the existing `[channelId+publishedAt]` compound index.
- Tombstone lookup uses the existing `channelId` index.
- Bilibili duplicate cleanup streams matching channel records instead of materializing the full
  channel collection.
- Adapter Post construction is centralized in `buildPost`.
- Platform cookie-auth detection is single-sourced in `platformAuth.ts`.
- UI write paths use the application services where those services carry meaningful mutation
  semantics; composition roots retain direct read-only assembly where another wrapper would add no
  value.
- Dead application facade code was removed.

## UI outcomes

- Six dashboard modals use a shared `BaseModal` with dialog semantics, Escape handling, focus
  containment, focus restoration, and body scroll locking.
- Repeated creator-view UI was extracted into `PlatformBadge`, `ChannelRow`, and
  `CreatorCardHeader`.
- `CreatorsView.vue` is smaller but remains a large view. Future feature work should extract its
  grid, list, detailed, and toolbar sections instead of adding more conditional branches.

## Verification

- `npm run typecheck`
- `npm test` — 37 tests across five files
- `npm run build`
- Production Vue SFC compilation
- SSR rendering checks for the extracted components and modal semantics
- One-time Dexie v3-to-v4 migration exercise covering post values, recycle-bin snapshots, and index
  queries

## Remaining product risks

These are product/runtime concerns, not known repository-secret leaks:

- Real Chrome extension verification is still required for alarm timing, DNR rule matching, content
  script messaging, and focus behavior.
- Private or undocumented platform APIs may change without notice.
- `FetchError` classification is structured but some broad adapter catch blocks can still classify a
  parse or authorization failure as a generic network error.
- Backup validation checks required fields but does not yet enforce full cross-table referential
  integrity.
- ESLint is not configured; CI currently enforces typecheck, tests, and production build.

## Repository privacy

- Build output, WXT state, browser profiles, logs, local databases, backup exports, environment
  files, and private-key formats are ignored by Git.
- No personal cookies, session tokens, API keys, or private keys are stored in tracked source.
- The Twitter web-client bearer value in source is a public web-client constant, not a personal
  credential; session identity is obtained only at runtime.

## The size concern is not borne out

| measure | value |
|---|---|
| `src/` + `entrypoints/` files | 113 |
| median / p90 file size | 111 / ≈380 lines |
| files over 500 lines | 10 |
| files over 800 lines | **0** |
| function bodies, p50 / p75 / p90 | 8 / 16 / 38 lines |

There is no 1,000-line file. The real signal is the **long function**, and there are exactly two
over 300 lines: `twitter.ts` `parseGraphQLResult` (~370) and `channelSync.ts` `updateChannel`
(~340). Both were examined specifically and both are correctly monolithic — the first shares
GraphQL level-probing state across every branch, the second is one database state machine for
`channel.id`. Splitting either would trade 40 local lines for a parameter object.

`douyinSnapshot.ts` (515) is the case that must *not* be split on principle: its injected probes are
serialized through `Function.prototype.toString()` and its scrape closure funnels every exit path
into one `finally` that clears the throwaway tab. Both invariants break under import-based splitting.

## What is actually worth doing

Ordered by value per unit of risk. None of these is a bug.

1. **`__END__` terminal-cursor semantics are implemented three times.** `historySync.ts:16-46`
   (early return + a Douyin special case), `historySync.ts:110-115` (same rule again inside the dig
   loop, with the comment repeated verbatim), and `channelSync.ts:194,:394` (the write). A change to
   what "complete" means must be made in three places today. This is the highest-value item found.
2. **Twitter GraphQL `features` objects are duplicated verbatim inside one file** —
   `twitterTimeline.ts:76-141` and `:277-345`, the second being the same content re-declared for the
   injected script. X changing a flag today means editing two literals 200 lines apart.
3. **The tri-state tag filter exists twice**, `useFeedFilters.ts:82-118` and
   `useCreatorDirectoryFilters.ts:133-155`, logic-for-logic identical (both were in one file before
   the `CreatorsView` split; the split did not cause it, it made it visible).
4. **Dry the `err instanceof Error ? err.message : String(err)` idiom**: two near-identical named
   `errorMessage()` helpers (`bgFetch.ts:26`, `proxyImage.ts:21`) plus ~10 inlined ternaries across
   adapters and composables. One `src/utils/` helper covers all of it.
5. **A dead application-facade method has a cause, not just an absence.**
   `postService.deleteToRecycleBin` (`postService.ts:31`) has no caller because
   `useDeletedPosts.ts:6` imports `deletePostAndTombstone` straight from the repository and bypasses
   the facade. Wiring the one call site through the service both revives the method and removes one
   of the 9 direct `infrastructure/db` imports AGENTS rule 8 carries as debt. That is the only
   instance of that debt with a named cause.
6. **Two of three recycle-bin restore functions are never called.**
   `postRepository.ts:63` `restoreDeletedPostId` is a bare alias for `restoreDeletedPost`;
   `:70` `restoreDeletedPostIds` duplicates the body of the *used* `restoreAllDeletedPostIds` minus
   the "all" scope. `:34` `registerAdapter` is likewise never called (adapters register statically).
   ~30 lines of dead surface in total.
7. **Adapters reach into `chrome.*` directly** — `bilibili.ts:426-429`, `weibo.ts:269-274`,
   `xiaohongshu.ts:254-259` (`chrome.cookies.get` for a login check) and `douyin.ts:68-82`,
   `twitter.ts:146-154` (`chrome.runtime.sendMessage`). This is outside every recorded rule: rule 8
   forbids repositories from importing `chrome.*` and says nothing about adapters. I verified it is
   **not** a correctness or security defect — the two `sendMessage` sites both guard on
   `IS_SERVICE_WORKER` first, so rule 6's self-messaging failure cannot occur, and the cookie reads
   only test presence; credential attachment still happens solely in `bgFetch` behind the
   `PLATFORM_HOSTS` allowlist. The cost is testability (adapters cannot run outside an extension)
   and five hand-rolled `typeof chrome === 'undefined'` guards.
8. **The popup loads all ten platform adapters it does not use.** `entrypoints/popup/composables/
   useQuickFollow.ts:9` imports `updateChannel` from `src/sync`, which reaches
   `platform/registry.ts` — and that file statically imports every adapter (lines 3-12). The build
   does split code, but `popup.html` `modulepreload`s the 256 KB shared chunk that holds them
   (verified: `popup.html` carries `<link rel="modulepreload" href="/chunks/main-*.js">`, and that
   chunk contains the Bilibili and Xiaohongshu adapter strings while the popup's own 31 KB chunk
   contains none). So a popup that follows one creator pulls every platform's parser. Size and cold
   start only — no correctness impact — and the honest fix (make the registry lazy, or give the
   popup a narrower sync entry) is a real change to how sync resolves adapters, not a one-liner.
9. ~~**`src/utils/http.ts` belongs in the chrome layer.**~~ **DONE 2026-09-11** (`B21`). It
   imported `infrastructure/chrome/messages/bgFetch.ts`, and `bgFetch` imports `utils/devLog.ts`,
   closing the repo's only cross-layer cycle. The cause was legitimate — rule 6 forces the service
   worker to call `performBgFetch` directly — but that justified the *edge*, not the file's address:
   the module is the network port every adapter fetches through (fan-in 9), and its direct mode
   reads `chrome.cookies` for Bilibili, so it cannot live below the chrome layer. It now sits at
   `src/infrastructure/chrome/http.ts`; `utils → chrome` is **0 edges** (was the cycle), and the
   dependency adapters always had is now visible instead of laundered through `utils`.

## What looks wrong and is not

- **`proxyImage.ts:8` holds a private `XHS_MEDIA_HOSTS` list**, which reads as a rule-2 violation.
  It is a strict subset of `PLATFORM_HOSTS` used to pick the mirror-rewrite path, and it is gated on
  `onPlatform` first, so it cannot widen access. Worth knowing: `tests/hosts.singleSource.test.ts`
  claims "the proxy keeps no private allowlist", but it only regex-checks for the *old* alternation,
  so this list is invisible to that guard.
- **`credentials` in `proxyImage` is computed once from the original host and reused for every
  mirror candidate** (`:75` → `:120`). Safe today because the candidate list contains only XHS
  hosts; newly unsafe the moment a non-platform candidate is appended.
- **The 8 substring host tests in `urlParser.ts`** (lines 57/84/99/135/161/185/200/228) are not the
  Douyin bug, and the distinction is worth stating precisely: Douyin's match decides *which real tab
  the extension will inject a collector into* (rule 9), so it must be hostname-exact; these eight are
  `bgFetch`-driven classification heuristics that discard the input host and rebuild `cleanUrl` on a
  hardcoded host, so a forged host cannot survive to any fetch. Credentials are decided separately
  in `hosts.ts`. A mechanical swap to the existing `isHostOrSubdomainOf` helper is worth doing for
  consistency, not for safety.
- ~~**`utils/http.ts` imports `infrastructure/chrome/messages/bgFetch.ts`**~~ — resolved by item 9
  above: the port moved into the chrome layer rather than gaining an injection layer.
- **Adapters now visibly import `infrastructure/chrome/http.ts`** (8 edges, all to that one file).
  Worth being plain about, because it looks like a new violation and is not: the dependency already
  existed — every adapter reached the chrome layer *through* `utils/http.ts` — and the move only
  stopped hiding it. `platform/registry.ts` is not involved.
- **`platform/registry.ts` statically imports all ten adapters** — that is not a layering violation
  (`platform` and `adapters` are the same layer), only the size consequence described in item 8.

**Corrected measurement.** The cross-layer numbers first reported for this audit were wrong. The
matcher resolved `../utils/http` with `Path(f).parent / spec`, which leaves `../..` in the *string*,
so `layer()` classified both endpoints as the caller's layer — every cross-layer edge counted as
same-layer, and the totals were inflated (339 edges reported, 273 actual; "longest chain 11
modules", actually 9). The one number that did reach this document, the port's fan-in of 9, was
recomputed with lexical normalisation and holds. The lesson is the same one this file already
records about scout findings, now applied to the parent's own arithmetic: a count from a matcher is
a lead until the resolver underneath it is checked.

## Platform module maintainability

Asked for separately from the findings above, and measured the same way (HEAD `4c89bb2`, each
number re-checked by hand — the first automated pass counted 15 "test files" for bilibili by
keyword, and missed RSS entirely because it imports its adapter through `await import()`).

| platform | lines | files | longest function | adapter tested directly? | verdict |
|---|---|---|---|---|---|
| douyin | 1052 | 3 | 167 (`fetchLatest`) | **yes — 3 test files**, plus `contract` and `collector` (6 files touch the handler) | healthiest despite being the largest |
| twitter | 594 | 1 | **256** (`parseGraphQLResult`) | **adapter yes** (`twitter.emptyTimeline`, 46 cases); **`twitterTimeline.ts` no** — 0 files reference the injected path | highest risk — and the injected path turned out to be dead |
| bilibili | 436 | 1 | **259** (`fetchLatest`) | no | branches dense, no net |
| xiaohongshu | 390 | 1 | **237** (`fetchLatest`) | no | same shape as bilibili |
| weibo | 324 | 1 | 163 (`fetchLatest`) | no | medium |
| fantia | 279 | 1 | 129 (`fetchLatest`) | no | medium |
| pixiv | 247 | 1 | 117 (`fetchLatest`) | no | medium |
| rss | 223 | 1 | 161 (`fetchLatest`) | **yes — real fixture XML** (9 + 5 + 18 cases) | the model to copy |
| youtube | 111 | 1 | 100 (`fetchLatest`) | no | small enough not to matter |
| withny | 97 | 1 | 82 (`fetchLatest`) | no | small enough not to matter |

**The common shape is the problem, not the size.** Nine of ten adapters are a single file with one
100–260-line `fetchLatest`, and the audit separately judged that shape *correctly* non-abstractable —
the parsing differs essentially by platform (Bilibili's two APIs plus a risk-control code,
Xiaohongshu's `window.__INITIAL_STATE__`, Weibo's mobile API with an Ajax fallback, RSS's
`DOMParser`). So this is not "nine copies that should be one"; it is **one shape repeated nine times
with only two of them under test.**

**Douyin is the counter-intuitive result and worth internalising.** It is the largest module set
(1052 lines across three files) and the only platform requiring throwaway-tab lifecycle management,
injection retries, and a terminal-cursor special case — yet it is the best-protected, because the
layer split (self-contained collector → validating contract → mapping adapter) is right *and* it has
five test files covering the hard parts. Complexity that is isolated and tested is not the same
thing as risk.

**Twitter is where to start, and the audit's own numbers were not enough to see why.** An earlier
pass of this measurement reported the Twitter adapter as untested; it is not —
`twitter.emptyTimeline` covers it with 46 cases, including the nesting-level, retweet-media and
appended-link defects. What had **zero** coverage was `twitterTimeline.ts` (486 lines): the injected
page script and the session/tab fallback. That is the half that talks to X, and B10's duplication
lived there.

**And it was dead.** Acting on the finding exposed a live bug that no measurement on this page could
have shown: the injected function read `Bearer ${TWITTER_BEARER_TOKEN}`, a module-scope constant, and
`chrome.scripting.executeScript` serializes the function with `Function.prototype.toString()` — so in
the page it threw `TWITTER_BEARER_TOKEN is not defined`, was swallowed by the injected function's own
try/catch, and returned a plain failure. Every Twitter sync fell through to the direct cookie fetch,
and `PLATFORMS.md` §2.2's advice to open the creator's profile and retry ("the extension reuses the
tab's session") had never been able to work. Fixed 2026-09-11; the constants now travel through
`args`, and the built bundle confirms `func:async(e,t,n,r,i)=>` reading `i.bearer`.

Three things this says about measuring a codebase, in order of how much they cost:

- **Coverage gaps hide bugs, not just risk.** "This module has no tests" reads as a debt; it was in
  fact an announcement that nobody could have noticed a broken path.
- **A count is not a diagnosis.** The table above was correct and still would not have predicted a
  dead code path. Writing the missing test is what found it.
- **Rule 9 already said the injected function must be self-contained** — for Douyin. Twitter was
  never checked against it, and the failure mode is silence: the injected function catches its own
  errors, so a `ReferenceError` looks like a platform problem. Asserting "it did not throw" cannot
  see it either; the new test evaluates the function's *source* with no closure and asserts on the
  result.

Two things temper the adapter's coverage, both documented by the file itself: its payloads are built
by a `tweetEntry()` helper rather than captured, and its header records that an earlier version of
that helper **encoded the bug** (nesting one level too deep, matching what the parser happened to
read) — which is exactly rule 15's failure. So the fixtures prove the parser agrees with itself, and
the next time a real payload is available it should be captured verbatim and kept alongside them.

**RSS is the template.** `tests/rss.parse.test.ts` drives the real adapter against real feed XML
(9 cases), `rss.content.test.ts` covers the size boundary (5), `rss.repair.test.ts` covers the stored-
row predicate (18). Feed XML is easy to capture honestly and X's GraphQL response is not, which is
why RSS got there first and the others have not — worth saying out loud rather than treating the
gap as pure neglect.

Recommended order, by value per unit of cost: (1) cover `twitterTimeline.ts`'s injected path — it can
be done without a network or a session by extracting the injected function and asserting the request
it builds; (2) parse-function tests for Bilibili and Xiaohongshu, which needs the parsing section
lifted into a pure function first; (3) capture one real Twitter payload verbatim next time the
extension is run against x.com, and keep it next to the hand-built fixtures; (4) leave
Weibo/Fantia/Pixiv until something breaks; (5) record explicitly that YouTube/Withny are deliberately
untested rather than leaving the gap silent.

## Method note

Five read-only slices (layering, duplication, test health, big files, dead code) ran concurrently
against the frozen revision `4c89bb2`, with the parent neither reading the same files nor editing
anything while they ran.

**A defect in the parent's own verification tool, found while checking B11.** The render-comparison
tool added during the `CreatorsView` split (`e2e/creators-render.mjs`) captured the sort dropdown
mid-animation in steps 20–22. Two captures of the *same* build differed in exactly those three
steps, which is what exposed it: the dropdown is a Vue `<Transition>`, and this browser window is
off-screen and never composited, so its enter/leave transition never settles (rule 30 — no frames
means no `rAF`). Three consequences, stated plainly:

- The tool now closes the dropdown before capturing and asserts `aria-expanded` instead of
  photographing the open state; two captures of one build are byte-identical (22/22), and the
  assertions are stronger than the markup was (`aria-expanded=true`, the option list exists,
  Escape returns it to `false`, the trigger label becomes 手动排序).
- The three affected steps are precisely the manual-sort ones, which no refactor touched. The other
  nineteen — the three view templates, filters, sorts, tags, batch — were never flaky, so those
  comparisons remain valid evidence.
- The same pass showed the parent reading the DOM synchronously after a click, which reports the
  *previous* render; the `AppSelect` looked dead until the read moved behind an `await`. Same rule,
  and the reason the first rewrite of those steps failed.

Two of the five audit slices died on model unavailability ("the selected model is temporarily
unavailable"). The one that had been told to accumulate findings in a file cost 13 minutes and
delivered; the one that had not burned 28 minutes for nothing. A third instruction turned out to be
structurally impossible for half the batch: `scout` agents have no filesystem write at all, so
"write a checkpoint file" only worked for the `task` agent. **Recording partial findings during a
long read-only audit is not optional, and the instruction has to match the agent type.**

Every scout claim was re-checked by hand before being written down here, and three did not survive:

- one asserted the `/e2e` `.gitignore` entry for `probe-result.json` was ineffective because the
  file was tracked — `git ls-files` and `git check-ignore` both say it is untracked and correctly
  ignored, so the entry works and the README's promise of a sample file is the actual defect;
- one called `deleteToRecycleBin` the probable sole member of `postService` and proposed deleting
  the module — the module has three members and two live callers; the *finding* (the one method is
  dead) is right, the recommendation was not;
- one reported a 274-line `str` helper in `weibo.ts` — it is one line; the matcher had run to end
  of file.

The parent's own first-pass measurements were wrong the same way: a brace-matching pass missed
`twitter.ts` `parseGraphQLResult` entirely (object-method indentation) and so understated the
longest function in the repo, and the import-graph resolver left `../..` in the path string and
reported 339 edges where there are 273. A third pass then reported the Twitter adapter as untested
because its import scan only matched single-line `from '…'` specifiers and `rss`/`twitter` both
import through the multi-line form — which had reached the platform table in this very document
before being caught.

And one claim produced **no** measurement at all, only a misread: a test assertion written against
`rweb_enhance_cards_enabled`, a key that does not exist in the source (the real one is
`responsive_web_enhance_cards_enabled`). It failed, and the failure was briefly read as evidence that
the two `features` copies had drifted. They had not: three independent comparisons — text extraction
of both copies, runtime capture of what each path actually sends, and the new test that pins them
equal — all say the copies were identical. **A confident reading of a failing assertion is not
evidence; the assertion itself has to be right first.**

**Numbers from a matcher are a lead, not a result**, and the correction has to be published, not
quietly applied: a wrong row in a table of measurements is how the next reader is misled.

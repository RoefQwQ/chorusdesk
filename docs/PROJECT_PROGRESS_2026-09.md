## 一、相对最初状态的主要进步

### 1. 安全模型从隐式假设变为显式代码边界

最初，后台请求安全依赖 manifest 当前没有开放外部连接、调用方按约定传入安全参数，以及 URL 字符串中是否包含平台域名。

现在：

- URL 必须是 HTTP(S)。
- URL 不能包含 embedded credentials。
- 平台身份通过解析后的 hostname 精确或合法子域匹配。
- 平台 allowlist 只控制凭据，不限制用户 RSS 地址的可达性。
- BG_FETCH 固定为 GET。
- 调用方不能控制 credentials。
- privileged runtime message 集中验证 sender。
- 未知 message type 默认拒绝。
- DNR 只作用于扩展发起的请求。

项目不再依赖“当前配置大概安全”，而是由代码自身验证调用者、URL、方法和凭据策略。

### 2. 两个长期静默失效的核心功能获得根本修复

#### unread badge 与 bookmark 统计

IndexedDB 不为 boolean 建立有效索引项，旧实现却把 `isRead` / `isBookmarked` 作为 boolean 写入索引字段，导致查询永久返回 0 且没有异常。

现在：

- 持久化类型统一为 `0 | 1`。
- adapter、repository、UI 和查询保持一致。
- Dexie v4 migration 修复旧 posts。
- recycle-bin snapshots 同步迁移。
- 索引查询经过真实升级链验证。

#### 自动同步

最初同时存在两个断点：Service Worker 启动会重建并重置 alarm；alarm 即使触发，Service Worker 又会向自身发送无法接收的 BG_FETCH message。

现在：

- alarm 只在缺失或周期变化时创建。
- Service Worker 直接调用后台 fetch 实现。
- 页面路径继续经过受保护的 message router。

### 3. 数据写入策略从“尽量存入”变为“拒绝污染”

现在：

- 无稳定身份的条目直接跳过。

### 4. 错误处理从文本匹配升级为机器可读契约

最初 `FetchResult.error` 是任意字符串，同步层通过搜索 `429`、`403`、“已到达”等文案决定控制流，导致业务逻辑依赖本地化文本。

现在：

```ts
interface FetchError {
  code:
    | 'auth'
    | 'rate_limit'
    | 'network'
    | 'parse'
    | 'timeout'
    | 'not_found'
    | 'unsupported';
  message: string;
  retryable?: boolean;
}
```

结果：

- 同步层使用 code，UI 使用 message。
- 文案变化不再影响业务控制流。
- 未知平台明确报错，不再静默按 RSS 处理。
- 历史同步只有收到明确 `hasMore === false` 才确认结束。

  不记 Cookie、Token、请求头或响应体（面板的用途就是被截图）。已写入 AGENTS.md 规则 11。

### 15. 第五批：开发者日志实测暴露的两处缺陷（2026-09-10）

第四批新增的开发者日志面板在真实使用中立刻产出两类发现——这正是它存在的理由。

**详细模式形同虚设（已在 P7 清单中预期到的风险，实际比预期更严重）**

用户开启详细模式后日志无任何变化。根因是三个缺陷叠加：

1. 写入队列**先按 `verbose` 过滤、后读取开关**：过滤用的是本上下文模块变量里的旧值。
2. 开关此前只存 `chrome.storage.session`：Service Worker 被回收重启后即以 `verbose=false`
   醒来，而**恰恰是 worker 在记录 `bgFetch`**——面板是页面，开关却在别的上下文被消费。
3. `debug` 行在记录时即被丢弃，而非在持久化时按开关裁决。

修复：开关优先读 `chrome.storage.local`（跨 worker 重启持久）、`session` 作回退，`setVerbose`
写两处；过滤移到读开关之后并在每次写入时重读；关闭详细模式时顺带清理缓冲里遗留的 `debug` 行。
变异验证：删掉「读开关」两行 → 2 项失败；开关退回 session-only → 1 项失败。

**空结果被当成「同步成功 0 条」——三个平台同时中招**

详细模式显示：4 个 Twitter 渠道均为「平台返回 0 条，hasMore=false」，且 `hasMore=false` 意味着
解析器连底部游标都没找到——即 GraphQL 返回**一个推文条目都没有**，却被报为成功同步。
小红书同样：主页初始状态里没有笔记时返回空成功。对照同批日志，bilibili / 抖音的 0 条是
适配器内部按水位线过滤的结果（两份日志的 `平台原始` 计数可区分），微博 / YouTube 返回 10 条后
由 `channelSync` 过滤——这两种 0 都正常。

修复：Twitter 解析器统计过滤前的推文条目数，为 0 时返回 `parse` 错误并说明常见原因；
小红书在 `rawNotes` 为空时返回 `parse` 错误；bilibili / 抖音 / 小红书补 `totalFetched`
（过滤前原始条数），`channelSync` 日志新增「平台原始 N 条」。已写入 AGENTS.md 规则 13。

风险等级说明：普通同步下空成功只是误导；但**历史回溯时 `hasMore === false` 会把游标写成
`__END__`**，虚假的空成功会永久封死该渠道的回溯——与规则 10 记录的回溯缺陷同一形状。

**顺带补强日志判据**：`channelSync` 成功行新增「平台原始 N 条」与「仅原创=是/否」。
后者是因为 Twitter 的原创过滤发生在**注入页面的脚本内部**，不过 `channelSync`——
「仅原创=是 + 0 条」可能是转推被滤掉（正常），「仅原创=否 + 0 条」则必是采集失败。
实测复验：Twitter 四个渠道均为「平台原始 19~21 条 / 平台返回 0 条」——载荷正常，
0 条来自「仅原创」在页面脚本内滤掉转推，即修正后的日志已能自证此前那批 0 条的性质。

### 17. 第七批：Twitter 全部账号产出 0 条的定位（2026-09-10）

**已由日志排除的原因**：水位线=无 → 不是「已缓存所以过滤掉」；平台原始 17 条 → 报文正常返回、

### 18. 第八批：Twitter 解析器的路径深度缺陷及其同类（2026-09-10）

第七批的探针一次同步即定性，用户回传的 warn 给出了确切答案：

```
转推跳过 0，解析失败 20；首条结构：条目 #1 无 tweet_results.result
（itemContent 键：__typename,itemType,socialContext,tweetDisplayType,tweet_results）
```

**根因**：`itemContent.tweet_results` 存在，但解析器读的是
`itemContent.tweet_results.tweet_results.result`——**多了一层**。真实载荷是单层
`tweet_results.result`，所以每个条目都解析成 `{}`，全部 Twitter 渠道**在任何报文下都恒定产出
0 条**，且不报错、不告警、`hasMore=false`。

**同时发现的第二个缺陷**：原本用于兜底的

```ts
asRecord(asRecord(asRecord(itemContent.tweet_results).tweet_results).result) ||
asRecord(asRecord(asRecord(item.itemContent).tweet_results).result)
```

**右侧分支是从不执行的死代码**——`asRecord()` 对 miss 返回 `{}`，而 `{}` 在 JS 里是 truthy，
左侧永远为真。也就是说「多一层」这个错误连兜底都被自己屏蔽了。

**测试为何没拦住**：`tests/twitter.emptyTimeline.test.ts` 的 fixture 当时按**错误形状**
构造（`tweet_results: { tweet_results: { result } }`），于是测试通过并把 bug 固化成「真值」。
这比没有测试更糟——它把缺陷写成了规范。fixture 已改为真实单层形状，并保留旧双层形状作为
兼容用例；变异验证：还原旧取值路径 → **4 项失败**。

**同类缺陷全仓清扫**。`asRecord(a) || asRecord(b)` 这一写法在仓库中共 3 处，全部是死兜底：

| 位置 | 影响 |
|---|---|
| `twitter.ts` 作者元数据 `coreUserResults` | **TweetWithVisibilityResults** 类推文取不到作者名/头像（`core` 在下一层） |
| `twitter.ts` 转推 `rtLegacy` | 可见性受限的转推取不到原推正文 |
| `xiaohongshu.ts` `card` | `asRecord(item.noteCard) || item` 的兜底永不生效 |

新增 `firstFilled(...candidates)`（`src/utils/json.ts`）表达「取第一个有内容的候选」，
并附注释说明为何不能用 `||`。三处改用该函数，并新增可见性受限推文的作者元数据测试
（变异验证：还原该行 → 1 项失败）。

**教训（已写入 AGENTS.md 规则 15）**：

1. `asRecord()` 永不返回假值，任何以它作为 `||` 左值的兜底都是死代码。
2. **测试 fixture 必须来自真实载荷**。按解析器当前行为「对拍」出来的 fixture 只能证明解析器
   和自己一致，无法证明它和平台一致——本缺陷正是这样躲过了类型检查、lint 与 187 项测试。
3. 探针式诊断（记录键名与布尔值）在无法本地复现真实报文的场景下，比继续加断言更有效：
   一次用户同步即定位到具体层级。

### 20. 第十批：首屏图片空白约 8 秒（2026-09-10）

用户报告首屏图片长时间空白占位、约 8 秒后才出现。定位到**三个叠加的性能缺陷**，
根因在文件系统句柄的读取路径：

**1. 每次读取都重开 IndexedDB 并反序列化目录句柄（主因）**

`getSavedRootDirectoryHandle()` 每次都执行 `indexedDB.open('FeedHubFSCache', 1)`，
再把存储的 `FileSystemDirectoryHandle` 结构化克隆取出。而它的调用方是**热点**：
每个已挂载卡片的每个媒体项都会调用一次。

首屏 ~12 张卡片 × ~2 张图 ≈ **24 次数据库打开 + 24 次句柄反序列化 + ~72 次目录查找
+ ~120 次文件探测**，全部与正在下载的图片争抢主线程与 I/O。已改为**会话级缓存**：
连接与句柄各缓存一份（`onclose`/`onversionchange` 时失效，`bindDirectory`/`unbindDirectory`
时清除），失败不缓存。这消除了主要成本。

**2. 未命中结果被反复探测**

图片不在磁盘时，每次卡片挂载都重走一遍「3 层目录 + 5 种扩展名」的探测。新增
`knownMissingMedia` 会话级负缓存（遇到真实磁盘错误时不记录，避免把暂时失败固化为永久隐藏；
目录换绑时清空）。同时把 `onMounted` 的串行 `for await` 改为 `Promise.all` 并行。

**3. 先发网络请求、再被本地命中作废**

`<img :src>` 首帧就指向网络 URL，磁盘探测稍后命中时 `src` 换成 blob URL——
而**浏览器在 `src` 变化时会中止进行中的图片加载**。于是每张已缓存图片都白白发了一次请求，
占位一直持续到探测返回。现在 `<img>` 在探测完成前不渲染（显示同尺寸的脉冲占位，避免布局跳动），
探测结束后一次性给出最终 `src`，不再有请求作废与中途换源。

**4. 新增耗时探针**：单卡片磁盘探测超过 1500ms 时输出 warn（`media` scope），
否则记 debug。这样「图片慢」若再次出现，日志会直接指出是哪一段慢，而不是继续靠感觉判断。

**验证**：新增 `tests/fsManager.caching.test.ts`（5 项：只打开一次 / 只读一次 /
未绑定也缓存 / 保存后即时可用 / 解绑后不复活），变异验证命中 4 项。测试总数 195。

### 21. 第十一批：抖音「必须先打开该创作者页面」的由来与空网格保护（2026-09-10）

用户质疑：「我开着抖音页面不就应该可以根据抖音的继续尝试同步吗，为啥我一定要去打开这个作者页面」

**代码真相**：`handleDouyinSnapshot` 的选页逻辑是

```
优先：任意正在浏览该创作者的 douyin.com 标签页
其次：任意 douyin.com 标签页 —— 找到后会把它导航到目标创作者主页再采集
```

也就是说**创作者本人的页面从来不是必要条件**，任意抖音页面都可以：扩展会自己导航过去。
硬性前提只有一个——**必须存在某个 douyin.com 标签页**（后台 `fetch` 抖音只会拿到反爬外壳，
`chrome.scripting.executeScript` 需要真实标签页承载页面脚本）。

**但三处缺陷让这个前提显得比实际更苛刻**：

1. **报错文案夸大要求**：原文写「请在浏览器中打开该创作者主页（douyin.com）后再同步」，
   而实际任一抖音页面即可。已改为「任意抖音页面」并说明会自行导航。
2. **没有页面时不自动开页**：Twitter 路径在找不到标签页时会
   `chrome.tabs.create({ active: false })` 开一个临时页、采集后关闭；抖音没有，
   于是「零抖音页面」时直接失败。已在抖音补齐同样行为——**手动同步不需要任何前置条件**。
   此处开页是安全的：自动同步在 Service Worker 中运行，而抖音适配器在 SW 里于发消息前
   就返回 unsupported（`douyin.ts` 的 `IS_SERVICE_WORKER` 分支），因此**定时任务永远不会
   走到这个开页路径**；原注释担心的「定时任务反复加载主页触发风控」不成立。
   临时页在 `finally` 中关闭。
3. **空网格被当作「已到底」**（即第六批遗留的 `douyin/uimi 平台原始 0 条, hasMore=false`）：
   普通同步（非深挖）路径上，`hasMore` 由 `truncated ? undefined : false` 决定，而 `truncated`
   在 `statedTotal === 0` 时对非深挖恒为 false —— 于是**空快照直接输出 `hasMore: false`**，
   `channelSync` 据此写入 `__END__`，**永久封死该渠道的历史回溯**。这与 AGENTS 规则 10 记录的
   正是同一形状：**证据不足却宣称已到底**。

   已改为：`snapshot.items.length === 0` 时返回 `parse` 错误（页面显示有 N 篇却读出 0 篇时
   在文案中给出该数字），且**绝不输出 `hasMore: false`**。空网格是「没观测到」，不是
   「观测到结束」。

**验证**：新增 3 项测试（普通同步空网格不宣称到底、空网格与 statedTotal 矛盾时点名数字、
深挖空网格同样不宣称到底），变异验证命中 3 项。测试总数 198。

**结论**：用户不再需要预先打开任何抖音页面——点同步即可，扩展会自己开/用标签页；
且即使页面没渲染出来，渠道也不会被误标为「已到底」。

### 22. 第十二批：临时标签页未关闭与图片加载阶段归因（2026-09-10）

**临时标签页残留（用户实测发现）**

第十一批新增「无抖音页面时自建临时页」后，用户实测：同步成功但**临时页没有关闭**。
根因是**清理时机**——原实现把 `tabs.remove` 放在 `finally`，而 `sendResponse` 在 `try` 内：

`sendResponse` 会关闭消息通道，此后 Service Worker 可能被立即回收，`finally` 中那个
**异步** `tabs.remove` 便不保证执行完。已改为**先清理、后响应**：把采集主体抽成
返回响应对象的 `scrape()` 函数，清理放在外层 `finally`，`sendResponse` 置于其后。

**修复过程中自己踩了一次同类坑**：第一版改造把 `fail(...)` 改成「赋值 + `return`」，
而 `return` 位于外层 `try` 内——它会**直接退出整个函数**，跳过 `finally` 之后的
`sendResponse`，于是所有失败路径都不再应答。已由 `scrape()` 返回值的结构消除该可能：
任何退出路径都必须经过同一个清理 + 响应出口。这条也说明了新加的 6 项测试的价值——
它们在改造中途就抓住了这个问题（失败路径超时无响应）。

**验证**：`tests/douyin.tabLifecycle.test.ts` 6 项（自建页在响应前关闭 / 失败时也关闭 /
解析失败时也关闭 / 绝不关闭用户已有标签页 / 已在目标页时不导航不新建 / 恰好响应一次），
用假时钟驱动 `waitForTabLoad` 的固定等待。变异验证：改回「先响应后清理」→ **3 项失败**。

**图片延迟归因**

用户报告：主界面点击左侧平台筛选后，**较早的微博/小红书博文**约 1–2 秒才显示图片；
其余平台图片正常。已排除本轮之前的修复（负缓存与句柄缓存已在），本轮进一步消除一处
**确定性冗余**——`getExistingNestedDirectory` 按媒体项重复调用，一张 9 图博文要走 9 次
相同的三层目录树（27 次 `getDirectoryHandle` 往返），现按目录段 memo 为 1 次；
写入路径创建目录后同步更新该 memo，换绑/解绑时清空。

同时本轮新增两个耗时探针，把「图片慢」从主观感受变成可归因数据：
`PostCard` 的磁盘探测（>1500ms 报 warn，已有）与 `media.ts` 的**图片代理往返**
（记录主机、耗时、体积；成功记 debug，失败记 warn）。此前的假设是「代理往返是慢的那一段」，
但**尚未被数据证实**，故先埋点而非直接改流程——若下一轮日志显示代理耗时占比很小，
说明瓶颈在直连网络或 DNR 命中，需另查。

### 23. 第十三批：图片延迟的真凶是上一批自己加的门闸（2026-09-10）

用户回传详细模式日志，两项数据直接定性，无需再猜。

**图片 1–2 秒：是第十二批那个 `<img>` 门闸造成的**

日志证据：

- 每一次探测都很快（0–390ms，多数 <200ms），且**全部命中**（`命中 N/N`）；
- **没有任何 `图片代理` 行** → 代理路径从未被调用，图片全部来自本地磁盘；
- 但探测的时间戳跨度是 **15:16:36.078 → 15:16:39.748 = 3.7 秒**（约 100 张卡片）。

单次快、总体慢。原因是我在第十批为了避免「先发网络请求再被本地命中作废」而加的门闸：
`<img>` 必须等 `mediaProbed` 置位才渲染，而**每张卡片都在 `onMounted` 立刻探测**——
包括视口外几千像素、根本还看不见的卡片。于是最后一批卡片的图片要等整个探测队列走完，
即 3.7 秒。**浏览器的 `loading="lazy"` 本来就在延迟网络请求，而我的 JS 探测无视了这条规则，
结果它自己成了瓶颈。**

修复：探测改为由 `IntersectionObserver`（`rootMargin: 800px`）触发，只在卡片接近视口时才走磁盘。
视口内的卡片立刻探测，视口外的滚动到时再探测——与 `loading="lazy"` 的语义对齐。
不支持 `IntersectionObserver` 或拿不到元素时回退为立即探测，避免图片永远不显示。

**另一个已可确认的事实**：这台机器上的磁盘探测本身已经很快（多数 <200ms，不少 0–100ms），
说明第十批的会话级句柄缓存与负缓存都在生效——第十批之前那次 8 秒的探测已不复现。

**微博/小红书图片正常显示** → 也顺带确认 P7 第 ② 项通过：
`declarativeNetRequestWithHostAccess` 仍然命中防盗链规则。

**Twitter「只有图片没有正文」：不是解析缺陷，是增量同步的语义**

WARN 给出 `full_text 长度=23；note_tweet 长度=0`。23 字符正好是一条 `t.co` 短链的长度，
而长文正文（`note_tweet`）为空——也就是说**这两个账号的这批推文，平台返回的正文本身就是一条链接**。
解析器没有漏读。

用户遇到的「同步修不好」另有原因，且是**设计使然**：

- **普通同步永远是增量的**：`channelSync` 用「已存最新 `publishedAt`」做水位线，
  只写入比它更新的内容，**从不改写已有行**。这正是增量同步便宜的原因，
  也意味着**普通同步在原理上不可能修复任何已存数据**。日志中每条 Twitter 都是
  `新增 0 条`（`水位线=9/9 22:21` 等），即适配器返回的 10 条全被判为已知后丢弃。
- **只有强制刷新会改写已有行**：`Shift + 点击`渠道行的刷新图标（按钮 tooltip 已说明）
  会绕过水位线并 `bulkPut` 全部返回内容，这才是修复旧数据的唯一途径。

已把这条契约固化为 `tests/channelSync.repair.test.ts`（2 项：普通同步不改写已有行、
强制刷新改写），变异验证命中 1 项（把增量过滤去掉 → 普通同步用例失败）——
因为「怎么修数据」的建议直接依赖这两条行为，改动任一条都会让建议失效。

**待确认**：探针已扩展为输出 `truncated`、`entities.urls` 数量与 `display_text_range`。
下一次同步即可判定这批推文是「作者确实只发了链接」（`entities.urls ≥ 1`）还是
「平台截断、正文未随响应下发」（`truncated=true`）——前者无需处理，
后者需要改走别的取文路径。

### 24. 第十四批：临时标签页补可自愈回收、正文复读与 RSS 全文（2026-09-10）

用户第二次报告同一现象。复盘：第十二批把清理从「响应之后」移到「响应之前」是**必要但不充分**的

本轮补上**无法泄漏的兜底**（并承认上一轮判断不充分）：

  （用户若在那个标签页里顺着链接跳走了，它已属于用户）。

这样即使存在我没预见到的第三条泄漏路径，残留也会在下次 worker 唤醒时被回收，而不是永久留下。

### 25. 第十四批补记：回收机制的安全边界与一个真缺陷（2026-09-10）

用户提问：「开着抖音标签页时同步，会不会错误地把我的标签页关掉」——这一问促成了两项改动，
其中一项是**此前残留的真正原因**。

**安全边界（回答用户的问题）**

结论是**不会**，依据在代码结构而非概率：

- `tempTabId` 与 `rememberTempTab()` **只在我们自己创建标签页的那条分支里赋值**。
  用户已有抖音页面时走 `else` 分支（只 `navigate`），两者都不设置 ——
  清理与回收**在结构上无法触及该标签页**；
- 记录只在创建分支写入，故回收只可能作用于扩展自己开的临时页；
- `chrome.storage.session` **随浏览器会话结束清空**，而标签页 id 在会话内唯一不重用，
  因此一条旧记录不可能在用户后来新开的标签页上兑现；
- 本轮新增**「正在查看的标签页绝不关闭」**守卫，覆盖 id 记账无法排除的唯一情形
  （我们的临时页被用户当浏览页用）。已用测试钉住。

**发现并修复的真缺陷：删除失败时记录被一并清除**

```ts
await chrome.tabs.remove(tempTabId).catch((e) => devLog.warn(...));
await forgetTempTab();   // ← 即使删除失败也执行
```

后果：`tabs.remove` 一旦失败，回收记录被删掉，而标签页仍在 —— **兜底再也找不到它，
该标签页被永久遗弃**。这正是用户仍看到残留的原因：第十二批的「先清理后响应」消除了
worker 被回收的时序问题，第十四批的兜底提供了第二条回收路径，但这条代码在失败时
**把两条路径同时断掉**。

已改为：仅在确认标签页确实消失（`tabs.remove` 成功，或 `tabs.get` 返回空）后才清除记录；
失败则保留记录并在日志中说明「已登记待下次启动回收」，由下次 worker 启动的回收重试。
回收函数中的同型写法也一并修正（删除失败不再清记录）。

**验证**：标签页生命周期测试 8 项（新增：删除失败必须保留记录、成功必须清除记录），
回收测试 8 项（新增：绝不关闭正在查看的标签页、删除失败保留记录、id 不存在时清记录）。
变异验证：去掉 `if (closed)` 包裹 → 失败保留用例失败；去掉 active 守卫 → 对应用例失败；
在回收中改为无条件清记录 → 对应用例失败。测试总数 **232**。

### 26. 第十五批：媒体推文的链接正文、全宽阅读视图与 RSS 自动补全（2026-09-10）

### 27. 第十六批：不再触碰用户标签页、媒体链接的兜底判定、溢出测量（2026-09-10）

### 30. 第十九批：RSS 不是「文本太长」，是「文章被压平了」——结构化正文与净化边界（2026-09-11）

用户看过第十八批的修复后给出关键反馈：*「虽然能看新闻，但是图片全都到最下方，不是针对 RSS 的特化
内嵌式阅读器方案，并且也没有排版」*。日志同时给出第三条线索：

```
[WARN] page media: 图片代理 assets.juya.uk 失败 11ms | Image host is not allowed
[DEBUG] page media: 磁盘探测 2ms（命中 0/16）
```

前两条目视结论与这条 WARN 指向同一件事：**RSS 正文被扁平化成纯文本，于是文章的结构被丢掉了**。

**① 图片全在最下方，因为图片没地方可去。**

适配器只存 `content`（纯文本），`mediaList` 另存全部图片 → 卡片与阅读视图都只能把 `mediaList`
作为图库渲染在正文之后。实测该源一篇文章带 **23 张图**，卡片于是显示成「6 格 + 17」的占位网格。
不是图片加载慢，是渲染模型里根本没有「行内图片」这个概念。

**② 没有排版，因为标题与段落都退化成同一段文字。**

同一实测：`<content:encoded>` 里有 **71 个 `<p>`、8 个 `<h2>`、29 个 `<h3>`、29 个 `<ul>`、
50 个 `<li>`、24 个 `<hr>`、22 个 `<blockquote>`**。这些在纯文本里全部消失。

**③ `Image host is not allowed`：图片代理把「可达性」当成了「凭据」来管。**

`proxyImage` 对非 `PLATFORM_HOSTS` 的域名一律拒绝。这与 AGENTS 规则 3 是同一类错误的下一层：
**allowlist 管的是凭据，从来不是可达性**。RSS 源的图片可以托管在任何域名
（实测 `assets.juya.uk`），而代理是唯一能加载「防盗链 / 无 CORS」CDN 的路径——于是每张文章配图
都加载不出来（实测 23/23 张均为 HTTP 200，CDN 本身完全正常）。

**本轮改动**

| 改动 | 内容 |
|---|---|
| 新增 `src/utils/sanitizeHtml.ts` | 白名单净化器：允许的元素保留、未知元素**解包**（保留子节点）、`script`/`style`/`iframe`/`form`/`svg` **连子树丢弃**；URL **解析后校验协议**（非前缀匹配）；只序列化自己创建的节点 |
| `Post.contentHtml` | 新增字段，仅 RSS 设置：净化后的文章 HTML。`content` 仍是纯文本（搜索/过滤/预览用） |
| 阅读视图 | `v-html` 渲染结构化正文 + `.article-body` 标签级排版；纯文本正文仍走 `whitespace-pre-wrap` 保换行 |
| `standaloneMedia()` | 卡片与阅读视图共用的单一规则：有结构化正文时不再重复列出行内图片；音频/视频仍单独列出 |
| `proxyImage` | 移除平台域名硬拒绝；**任意 http(s) 域名可抓取，仅平台域名带凭据**（参考实现与截图：`assets.juya.uk` 现在可代理） |
| `assets/main.css` | `.article-body` 排版：标题分级、列表符号、引用、代码、表格、行内图片圆角与间距（含深色变体） |
| 存储上限 | 新增 `RSS_MAX_HTML_CHARS = 60000`（实测最大文章 HTML 28661 字符） |

**为什么净化必须发生在解析端而不是渲染端**：阅读视图用 `v-html` 渲染，而这是扩展页面、持有用户
cookie 的上下文。把净化放在适配器意味着**入库的数据已经是安全的**，任何渲染方都不需要记得
「RSS 内容不可信」。

**为什么不用正则清洗 HTML**：输入是拿到的字节，输出是**本函数自己创建的节点**的序列化。
按模式重写 HTML 是公认会留下绕过面的做法；构造新节点则意味着属性无法靠「大小写 / 多余字符 /
重复引号」之类的写法存活。

**验收状态**：typecheck（TS7 + vue-tsc）/ lint / **314 项测试（33 个文件）** / build / zip 通过。
新增 `tests/sanitizeHtml.test.ts`（23 项，全部是攻击用例，不是格式偏好）、
`tests/proxyImage.test.ts`（8 项，钉住「可达性≠凭据」两侧）、阅读视图结构化用例与
`standaloneMedia` 用例。

**变异验证**（每项都确认变异已生效）：
- 不再丢弃 `<script>` → 1 项失败；URL 不做协议校验 → 5 项失败；属性不再过滤 → 2 项失败
- 适配器不再设置 `contentHtml` → 2 项失败；**移除净化调用 → 1 项失败**

> 原始 HTML 恰好干净，断言即便在净化被移除时也通过。已改为在 fixture 的 `content:encoded` 里

**补充：文章内图片的兜底**。结构化正文里的图片是 `v-html` 内的普通 `<img>`，**无法挂载

`error` 不冒泡，非捕获监听器永远收不到），每个元素只尝试一次（`WeakSet`，避免代理也失败时
无限重试）。

**真实渲染验证**（不只是「测试通过」）：用真实源走真实适配器产出 `contentHtml`，配构建出的

### 31. 第二十批：风控延迟对策与紧凑列表对齐（2026-09-11）

用户反馈两条：*「查看同步和已绑定平台没对齐」*、*「我刚刚多次抓取触发了验证码风控，我们没做好
风控的延迟等待对策」*。日志同时给出了第三条证据。

**① 风控：延迟算错了地方。**

### 35. 第二十四批：注入「返回了」不等于「跑完了」——抖音失败的真因（2026-09-11）

用户日志里的数字直接定案：

```
22:36:41.586 FETCH_DOUYIN_SNAPSHOT
22:36:45.059 [WARN] 作品网格在等待时间内未渲染 | tab 689923812
```

**3.5 秒**就报「等待时间内未渲染」，而探针期限是 **10 秒**——**探针不可能说出这句话**，
它只在截止时刻返回 `false`。

真因：`chrome.scripting.executeScript` 注入的页面若发生跳转，**不会可靠地 reject，而是
resolve 且不携带结果**（脚本所在的帧没了）。旧代码把「调用 resolve 了」当成「脚本跑完了」：

```ts
.then((r) => r?.[0]?.result === true).catch(() => false)
```

于是「帧被销毁」与「页面确实没有网格」得到同一个答案。**那行日志本身是假的**，而且它把矛头
指向了页面，而不是我们自己。

修复：

| 项 | 内容 |
|---|---|
| 判定 | 统一 `injectAndAwait`：区分 reject / 无返回值 / 成功。注入的函数按构造要么返回布尔、要么返回对象，因此「没有返回值」即可靠地等于「没跑完」 |
| 重试 | 无返回值属**暂时性**，重试（上限 3 次）；探针与**采集器都重试** |
| 采集器分类 | 采集器**总是**返回对象（空网格返回空对象），所以「无结果」永远不是数据——但它此前被报成「未返回可解析的作品数据」，读起来和「该创作者没有作品」一模一样。现改为 `network`，并说明是页面跳转 |
| 诊断行 | 抖音标签页扫描不再在「没找到抖音页」时附警告——那正是**常规情形**（本处理器自己开临时页），几乎每次同步都触发，无病呻吟 |

**已写入 AGENTS 规则 23**，其中两条通用的：

- **日志里的时间矛盾是关于代码的 bug 报告，不是关于网络的。**「它在自己期限内就放弃了」是算术，
  瞬间定位到代码；先读数字，再谈平台。
- **诊断探针答完问题后就该停掉。**探针存在的意义是回答某个未知，一旦答案已知，它就从探针变成噪声。

**验收状态**：typecheck（TS7 + vue-tsc）/ lint / **412 项测试（36 个文件）** / build / zip 通过。

**变异验证**：把判定改回「任何 resolve 都算跑完」→ **5 项失败**，其中一项正是按日志形状命名的用例。

### 38. 第二十六批：抖音调研结论 + 真因定位（重试按次数是错的）（2026-09-11）

**① 架构差异（回答第二问）**：

|  | 标签页的角色 | 数据从哪来 |
|---|---|---|
| 推特 | **会话载体**（有 cookie + 同源即可） | 注入脚本直接调 **GraphQL API**，用户名是**参数** |
| 抖音 | **数据源本身** | 读**渲染出来的 DOM** |

推特复用任意 `x.com` 页面即可，因为 `/i/api/graphql/...` 只要求会话与同源；
抖音的 API 需要 `a_bogus`/`X-Bogus` 签名（见调研文档），**规则 9 明令不碰**，
所以只能读 DOM —— **必须在主页，且必须渲染**。这是设计代价，不是实现疏漏。

**② 调研结论**（写入 `docs/DOUYIN_RESEARCH_2026-09.md`）：
- **官方无合规路径**：`video.list`/`video.data` 只返回**授权用户本人**的作品，
  看别人的需要**那个人单独授权**。本项目核心用法**没有官方 API 解法**，必须如实说明。
- **社区共识恰好站在我们这边**：MediaCrawler 官方问答明确建议
  「**CDP 连接自己的真实浏览器**」以复用会话/profile、大幅降低风控。
  我们本来就是这么做的 —— 唯一缺的是**渲染**，而那是浏览器行为、不是反爬。
- **签名路线明确排除**（与规则 9 及上架定位不相容），已写进 `collector.ts` 注释。

**③ H1 实测：否定。** 桌面创作者页**确实**内嵌 JSON
（`<script type="application/json" id="RENDER_DATA">`，202KB），但内容是
**`app.tccConfig.*` 应用配置**（组件路由表、预载阈值、页脚链接），**不是作品数据**。
按 `/aweme|post|item_list|works|video/` 遍历整棵树，命中的全是配置键。
纯 HTTP 抓取则返回 `_$jsvmprt` / `__ac_` 混淆挑战壳。

> 顺带：`RENDER_DATA` 是**应用级配置，与登录态无关**，所以「登录后内嵌数据里就有作品」
> 这个假设既无证据也无必要 —— 而且**扩展本来就跑在用户已登录的浏览器里**。

**④ 真因（由日志时间线定案）：重试按次数是错的。**

```
23:20:04.708 FETCH_DOUYIN_SNAPSHOT
23:20:06.833 网格探针未完成，重试 1/2   ← 注入未返回结果
23:20:07.629 网格探针未完成，重试 2/2   ← 注入未返回结果
23:20:08.480 [WARN] 探针始终未能完成
```

三次尝试共 **1.6 秒**（每次失败约 1s），所以：探针**从未真正运行** →
**10s 预算一次都没被用上** → 循环在 **1.4s** 就放弃，而被等待的页面**约 10s 才水合**。

**一次廉价失败换来的是另一次廉价失败**，循环在页面还在加载时就宣布它坏了。

修复：重试改为 **20s 时间期限**（不是次数）。廉价失败 → 期限内尽可能多次；
昂贵情形（注入跑起来了）→ 不变，一次运行已花满预算并返回真实答案，直接短路。
采集器同期限 —— 它比探针更适合当重试目标：**一次调用同时回答「还没好」和「这是作品」**。

> **这是本问题的第二次修**。第一次把探针整个删掉，理由「异步注入会被跳转杀掉」，
> 结果**把等待从约 10.8s 砍到约 1.4s**，等于把原缺陷种了回去（用户发现，测试没发现）。
> **这一版的关键区别：每次尝试的预算原封未动，只改了尝试次数。**

**⑤ 顺带撤回一条不成立的说法**：规则 10 曾把「29 篇里加载出 18 篇」当作登录墙的证据。
既然标注数含隐藏作品，18/29 完全可能只是「11 篇隐藏 + 网格已完整」。
已在 AGENTS 规则 10 与 `collector.ts` 中标注该证据不成立。

**变异验证**：恢复「3 次上限」→ 2 项失败（含按本次日志形状写的那条）；

### 39. 第二十七批：紧凑列表按调研模式重做表头与展开控件（2026-09-11）

用户报了三次同一块区域，第三次给了明确的四条：
*「明细列没有用处」/「排序只有一个选项」/「表头点不了」/「网格和详细卡片也没有排序」*。

**① 前两次修改为什么都失败 —— 靠测量而不是推理定案。**

根因：展开按钮**位于「已绑平台账号」单元格内、徽章之后**，所以它的 x 取决于该行有几个
平台徽章。前两次修改都只在**该单元格内部**改排列（`justify-between` → 合成一个 flex 组），
而**一个随前序内容变化的位置，无法通过调整它自身所在分组的对齐方式修正**。

用真实构建样式表做的复刻页量 `getBoundingClientRect().x`，三行分别为 1 / 2 / 4 个徽章：

|结构|展开按钮 x|
|---|---|
|`justify-between`（最初）|805 / 805 / 805 —— 对齐，但被推到最宽列的极右|
|第一次修（合成一个 flex 组）|**482 / 512 / 575** —— 93px 锯齿，**用户箭头指的正是这个**|
|现在（行首 chevron）|31 / 31 / 31|

**② 采用调研到的模式，而不是自创布局。**

- **行展开控件 = 行首 chevron**（W3C Disclosure 模式）。放在单元格最前，x 天然与徽章数无关。
  同时删掉自造的「明细」列 —— 它是为「给展开按钮找个归属」而发明的，用户第一个就点了它。
- **表头排序 = W3C 可排序表格模式**：标签包在 `<button>` 里、`aria-sort` 只落在排序列上、
  按钮**铺满整个表头单元格**（`<th>` 用 `p-0`，按钮用 `py-2.5 px-3`），因此整格都是点击区。
  操作列不放按钮、不带 `aria-sort` —— 它装的是行操作，不是数据。

几何实测（隔离 Chrome，**不是用户的浏览器**，见规则 25）：五个可排序表头的
`fillW`/`fillH` 全为 `true`；`aria-sort` 仅在「创作者」为 `ascending`、其余 `none`、
操作列为 `null`；`td[colspan]=6` 与普通列数一致。
视觉复核：chevron 在头像左侧且垂直对齐、「创作者」显示上升箭头、其余列显示淡色双向箭头、
「明细」列与「查看全部」按钮**均已消失**。

**③ 方向不是多余的状态。** 单向排序回答不了显然的问题：「作品数」既想最多在前也想最少在前，
「创作者」既想 A→Z 也想 Z→A。引入 `creatorSortDir` 后，点击同列翻转，文字列默认 A→Z、
计数与时间列默认最新最大在前。比较器各分支**只陈述升序语义，方向统一施加一次**，
所以新增列不可能漏掉箭头。工具栏下拉与表头**共用同一份状态**（经 computed 中介），
两者在结构上不可能再互相矛盾。

**④ 回答第四问：网格与详细视图本来就能排序，是共享状态。**
三个视图都由 `filteredCreatorsList` 派生，表头点击与下拉都作用于它。新增两条测试

2 项失败。网格/详细没有列可点，所以那里**下拉是唯一入口** —— 它不在 list 分支内，
另有测试逐个视图确认「排序」控件存在。

**⑤ 测试重写为 13 条，全部变异验证：**

|变异|结果|
|---|---|
|点击同列不再翻转方向|1 项失败|
|比较器忽略方向|2 项失败|
|列构建器改用未排序数据|2 项失败|

**⑥ 我自己写错的两个测试（都靠失败暴露，不是靠推理）：**
- 复刻页的 `<svg>` **没有 path**，视觉复核因此报告「看不到图标」，而几何测量明明显示按钮

**⑦ 新增 AGENTS.md 规则 26**：*匹配不到任何内容的脚本会产生一个绿色的测试套件，而这个绿色是假的。*
本批有两次编辑「成功」但什么都没改 —— 其中一次是**用来证明测试有牙的变异**：它静默匹配到 0 处，

抖音采集依赖真实页面的渲染 DOM，由此带来与其余平台不同的边界：

- **DOM 结构耦合**：页面改版（滚动容器类名、网格节点、封面/标题选择器变化）会直接破坏采集器，且只能在真实页面中发现——fixtures 无法预警。
- **匿名截断**：未登录时抖音只放出部分作品（实测 18 / 29），剩余历史必须登录后才能回溯。
- **capability 边界**：与 Twitter 路径同属「借真实页面绕过反爬」的方案，平台风控升级或页面架构变化都可能使其失效，属于无法靠本地重构消除的外部依赖风险。

## 最终评价

本阶段实现了最初目标的大部分核心价值：

- 关闭凭据安全边界缺口。
- 修复 IndexedDB 静默索引失败。
- 修复自动同步双重断路。
- 阻止随机 ID、碰撞 ID 和 NaN 时间戳污染数据。
- 将字符串错误升级为结构化契约。
- 将关键规则转化为测试和 CI。

追加的抖音阶段在此基础上证明：即使面对无法后台化的平台，项目也能以隔离层 + 不可信输入校验的方式安全接入，而不削弱既有安全边界。

第二批（同日）完成 Rplay 平台卸载、ESLint 与 migration 永久测试三项收官：安全面减少一个
凭据暴露面与一个 content script 注入面，工程面补齐 lint 门禁并把历史 migration 契约钉进 CI。
ESLint 首轮扫描还捕获并修复了一个 UI 真回归（settingsContext 字段缺失）和一个交互真 bug
（刷新按钮双触发）——证明静态检查在缺乏 E2E 的项目里是有效的第三道防线。

项目质量的提升是结构性的，而不是表面增加功能。2026-09-10 的真实 Chrome 使用验证补上最后一块证据缺口后，项目已进入可用状态；~~剩余工作（migration 永久测试、token 姿态、CreatorsView 拆分、ESLint）~~ 中前三项已关闭，剩余工作仅 P4（CreatorsView 拆分）与待定的 P6（UI 重设计），均为非阻塞的打磨项。

第三批（同日）在真实 Chrome 中完成系统性界面走查并修复 14 项发现（3 项真实缺陷、11 项交互
与信息密度改进），同时把账号角色常量与下拉控件各自收敛为单一实现。两点经验值得保留：

- 「日常使用未发现异常」不等于「逐项走查通过」——P0 的日常验证通过后，结构化走查仍产出
  14 项发现，说明两种验证强度不可互相替代（手册 8.2 的检查方式分工）。
- ESLint 与逐项走查在同一批中分别捕获了测试与类型检查都覆盖不到的问题（settingsContext
  字段缺失、刷新按钮双触发、样式回退），关键路径之外的第三道防线实际起了作用。

第四批（同日）针对的正是前三道防线**共同的结构性盲区**：它们在「代码可运行、界面可操作」的
范围内有效，但对「文档宣告存在而代码里断路」「门禁根本没扫到目标文件」「失败表现为多做一次
而不是报错」这三类问题全都无能为力——

- 图片归档增量从上线起恒不命中，界面只显示「已缓存跳过 0 条」，一个看起来完全合理的数字；
- 抖音封面「走 Background 图片代理」被写进 PLATFORMS 文档与 P0 验证清单，而代理的白名单
  里根本没有抖音域名，该路径从未可执行；
- `tsc --noEmit` 命中 440 个文件、`.vue` **0** 个，于是 `CreatorsView` 引用了 9 次已删除的
  `isBatchMode` 也没人发现。

三条教训按价值排序：

1. **门禁要覆盖它声称覆盖的东西**。引入 `vue-tsc` 是一次命令的改动，换来 5 类真实缺陷立即
   暴露（含批量模式整体失效、一个从未渲染过的同步时间区块）。此前 CI 全绿的含金量低于它的
   字面含义。
2. **单一来源要真的单一**。`hosts.ts` 被文档称为唯一来源已有数月，但 manifest 与图片代理各
   自维护副本，代价是一个被文档承诺、实际 403 的代理路径。同一批把 manifest 改为派生生成，
   并加测试钉住——「已经有唯一来源」这句话本身需要一条测试来担保。
3. **静默失效需要专门的探测方式**。前三轮的走查方式（打开界面、逐项操作、观察反馈）对「结果
   依然合理」的缺陷无效。这类缺陷只能靠对照声明与实现来发现，或者靠埋点把「本该发生但没发生」
   变成可见信号——这也是本批新增开发者日志面板的动机之一。

同时补齐了工程链路的两处缺口：发布流水线（此前 README 引导用户去 Releases，仓库却没有
任何发布流程）与开发排查手段（此前打包后 Service Worker 的失败几乎不可观测）。

第四批之后（第五至十七批）全部由用户真机反馈驱动，其中反复出现的两类问题值得单独记录，
因为它们都不是「写错了一行代码」：

**其一：静态检查与走查都抓不到「文档承诺而代码断路」。** 三条防线（类型、lint、测试）
在「代码可运行、界面可操作」的范围内有效，但对三种形状无能为力——
① 文档或清单宣告某能力存在，而实现里根本没有那条路径（抖音图片代理）；
② 门禁没扫到该扫的目标（`tsc` 不解 `.vue`，于是 `CreatorsView` 引用了 9 处已删除的 ref）；
③ 失败形态表现为「多做一次」而非报错（归档探测恒不命中，界面只显示合理的「跳过 0 条」）。
第三类尤其危险：**它的结果看起来是正常的**。这也是本阶段新增开发者日志面板的直接动机——
把「本该发生却没发生」变成可观测信号。

**其二：修好适配器不等于修好数据。** 这个错犯了三次（推文正文、推特媒体链接、RSS 截断），
每次都是「验证了适配器返回的 Post 正确」就收工，而用户看到的始终是数据库里的旧行——
普通同步按契约只写水位线之后的内容、从不改写已有行。判断信号其实一直在日志里：
`新增 0 条` 配上非零的「平台返回」就说明什么都没写入。已固化为 AGENTS.md 规则 16。

两次「探针式诊断」证明，在无法本地复现真实报文的场景下，**记录键名与布尔值比继续加断言更有效**：
推特那条 0 结果的根因（`tweet_results` 多读一层）与媒体推文的链接正文（`display_text_range=0-0`），
都是靠一次用户同步的探针输出直接定位的，而非继续猜测。

| | 第一份 | 第二份 |

| 核心结论 | 外围防线专业化，核心领域模型没有 | **防御体系超前于领域模型与治理体系** |

## 2. 已核实的证据（P0：数据库可达矛盾态）

第二份审计的核心贡献。**这不是 bug 清单，是领域建模错误。**

### P0-1 `deletedPostIds` 一表两职 —— 把「永久意图」与「可回收物」塞进同一行

`src/infrastructure/db/postRepository.ts:33`

```ts
export async function deletePostAndTombstone(post: Post): Promise<void> {
  await db.posts.delete(post.id);
  await db.deletedPostIds.put({ id: post.id, ..., postData: JSON.parse(JSON.stringify(post)) });
}
```

同一行记录同时承担：

| 职责 | 语义 | 生命周期 |
|---|---|---|
| **A. 同步黑名单** | 「这个 ID 用户删过，别再抓回来」 | **应永久** |
| **B. 回收站快照** | 「还能不能找回」 | 可清空 |

两者生命周期不同，却共用一行。后果：

- `postRepository.ts:81` `permanentlyDeletePost(id) { await db.deletedPostIds.delete(id) }`
  ——**「彻底删除」删掉的是抑制状态本身**。该 post 当前确实不在了，但抑制也一并消失。
- `postRepository.ts:128` `clearDeletedPostRecords() { await db.deletedPostIds.clear() }`
  ——**「清空回收站」= 批量解除黑名单**。

**用户可见的后果**：点「彻底删除」或「清空回收站」后，下一次 force refresh / 深度回溯 /
重建库后的同步，**那些动态可以重新出现**。

`postService` 的注释写「Drop one tombstone for good (the post stays gone)」——**这句话是假的**。

**正确模型**（两者解耦）：

```
suppression      { id, channelId, deletedAt }      // 永不清，只增
recycleSnapshot  { postId, postData }              // 可清
```

或仍用一张表但 `suppressed = true` 与 `postData?` 分离：「彻底删除」只清 `postData`。

### P0-2 删除/恢复不是原子的

- `postRepository.ts:33` 删除：`posts.delete` 与 `tombstone.put` **两步、无事务**
- `postRepository.ts:50` 恢复：`posts.put` 与 `tombstone.delete` **两步、无事务**
- `channelSync.ts` 的 `restoreDeleted` 路径：**墓碑清理失败仍继续把 post 写回**

任一步失败即可进入：

```
posts[id] 存在   AND   deletedPostIds[id] 也存在
```

两个互相矛盾的事实同时成立。**Dexie migration 写得很认真，但业务上最需要事务的地方没有事务。**

### P0-3 级联删除留孤儿墓碑

`src/infrastructure/db/creatorRepository.ts:27`

```ts
await db.transaction('rw', [db.creators, db.channels, db.posts], async () => { ... });
```

事务与删除都**不含 `deletedPostIds`**（`deleteChannelCascade` 同）。而恢复单条不校验父实体
（`entrypoints/dashboard/composables/useDeletedPosts.ts:81` 只查 channel 用于是否走同步）。

可达路径：

```
删除 Post → 留墓碑+快照 → 删除其 Creator → creator/channel 消失、墓碑还在
→ 回收站点「恢复」→ Post 写回，creatorId / channelId 指向不存在的行
```

而 UI 此时弹的是「动态已定向找回！」。

**未定义的问题**：父实体删除后，子实体的回收站记录应该是什么生命周期？必须定规则。

### P0-4 备份不含负向意图

`src/infrastructure/db/backupRepository.ts:11`

```ts
export interface FeedBackup {
  version: '1.0'; exportedAt: string;
  creators: Creator[]; channels: Channel[]; settings: AppSettings; posts: Post[];
}
```

**没有 `deletedPostIds`。** 用户语义上：

```
我关注谁      → 备份了
我收藏什么    → 备份了
我看过什么    → 备份了
我明确说过「不要再给我看」 → 没有
```

对信息聚合器而言这是严重缺口。而 UI 弹的是「已成功将**完整数据**备份写入」。

**用户可见的同一承诺还有 README**（`:33`）：「支持将**全部数据**导出为单个 JSON 文件备份，
便于**跨设备迁移或重装恢复**」——正好是那条会出事的路径（迁移/重装 → 导入 → 删过的动态回来）。

> 该句不是用户所写（README 系早期 Gemini 起草，方向大致与当时开发方向一致，
> **不作为决策论据**，见 §6）。这里记录它只是标明：**方案 A 落地后这句自动成真**，
> 无需单独改文案；在那之前它属于同一处过度承诺的用户可见面。
> 若 A 迟迟不做、而希望先如实说明，则需另外决定——**目前不做**。

### P0-5 「恢复备份」实为 merge

`backupRepository.ts:105` `restoreBackup` 只 `bulkPut`，**无 `clear`**。

```
现库 A B C D  +  旧备份 A B  →  「恢复」后仍是 A B C D
```

即 **overlay import**，不是 snapshot restore。新设备场景无碍（库本来空），但名字对不上。
两者都有价值，应显式区分：

```
恢复快照  = 清库 → 写入备份
合并导入  = 保留现有 + 覆盖同 ID
```

## 3. 已核实的证据（P1：失败语义与边界）

### P1-1 失败域混在一起，写库失败被分类为 `network`

`src/sync/channelSync.ts:522`

```ts
} catch (err: unknown) {
  const structured = err instanceof FetchTimeoutError
    ? fetchError('timeout', err.message)
    : err instanceof Error ? fetchError('network', err.message)   // ← 任何 Error
      : fetchError('network', '未知异常');
```

`db.posts.bulkPut` / `db.channels.update` / Creator 元数据写库失败，**全部变成「平台网络错误」**。

**而 `code` 不是文案**——它驱动 persisted cooldown、游标终态、用户动作。bilibili `-412`
事故已经证明这个形状：**一个错误分类不仅说错话，还会执行错误策略**。

### P1-2 timeout 是「停止等待」而非「停止任务」

`channelSync.ts:143,179`：`Promise.race([adapter.fetchLatest(...), timeoutPromise])`。
全树**无 `AbortSignal`**（已 grep：`src/adapters/types.ts`、`src/sync/` 零命中）。

45 秒后 Chorus 不等了，但底层 fetch / Twitter 页面采集 / 抖音临时页 / 多请求 enrichment
**可能仍在执行**。于是：

```
请求 A 超时 → UI 报失败 → 用户立刻重试 B → A 其实没停 → A + B 同时打平台
```

刚刚建好的 pacing/cooldown 可被这个「幽灵请求」绕过。

### P1-3 `FetchResult` 无法表达「降级成功」

`src/adapters/types.ts`：只有 `posts / error? / hasMore? / totalFetched?`，**无 partial/degraded**。

但平台已是多来源 best-effort 聚合（bilibili 动态 + medialist；XHS 主列表 + enrichment；
Twitter 标签页 + 直连兜底）。于是会出现**最危险的失败形态**：

> 不是报错，而是**安静地少数据**——用户以为「这个人没更新」，实际是一条采集路径坏了。

### P1-4 `urlParser` 有 8 处 `host.includes()`

`src/utils/urlParser.ts`：`:57` bilibili、`:84` twitter/x、`:99` youtube/youtu.be、
`:135` pixiv、`:161` fantia、`:186` xiaohongshu/xhslink、`:214` weibo、`:44` rsshub。

而**同一文件 `:315` 的注释自己写着**为什么这是错的（`douyin.com.attacker.example`），
并且只有抖音用了 `isHostOrSubdomainOf`。

`AGENTS.md` 规则 1 的原始事故形状，**只修了 `hosts.ts` 与抖音**。当前不构成 authenticated
SSRF（background 层另有严格 allowlist），但属**输入分类错误 + 安全边界不一致**。
**`tests/` 下无 `urlParser.test.ts`**（已确认）。

### P1-5 占位名靠字符串形状猜测

`channelSync.ts:406` 两份手写前缀列表（channel 名 / creator 名），注释承认两者曾 drift。

## 6. 已决定：备份纳入抑制记录（方案 A）

**2026-09-12 用户决定，取 A。**

### 决定内容

备份格式从 4 节扩为 5 节，**纳入 `deletedPostIds`**：

```ts
// 现状
FeedBackup { version: '1.0'; exportedAt; creators; channels; settings; posts }

// 目标
FeedBackup { version: '1.1'; exportedAt; creators; channels; settings; posts; deletedPostIds }
```

语义变化：备份从「**导出当前可见内容**」变成「**应用状态的快照**」——导入后是「我当时的样子」，
含「我当时明确不要的东西」。

### 选 A 而不选 B 的理由（不依赖任何文档的承诺）

**决策依据是行为本身**：导出一份备份、清库、导入回去，**用户删过的动态会重新出现**。
这一条在 README 写什么之前就成立，也无论 README 怎么改都成立。

- **B（改文案）不解决它**，只是让用户更早猜到。而且「导入备份」这个动作本身就承载
  「恢复我当时的全部」的预期——把「完整」二字删掉，用户**不会因此少惊讶一次**。
- **A 是 P0-1 的必要前置**。P0-1 要把抑制拆成独立表；若备份不含抑制，**拆完之后备份仍然残缺**，
  等于同一件事做两遍。

> 附带说明：README 当前的「支持将全部数据导出…便于跨设备迁移或重装恢复」不是本决策的论据来源
> （该文案非用户所写）。上表两段是**独立成立**的理由。

### 实施要点（已核实的成本）

| 项 | 结论 |
|---|---|
| 版本号 | 必须 `'1.0' → '1.1'`——解析器是 `data.version !== CURRENT_BACKUP_VERSION` 就拒（`backupRepository.ts:135`），不升版本会**直接拒绝新文件** |
| 旧文件兼容 | **成本低**：解析器已用 `!== undefined` 的宽容写法，`'1.0'` 文件缺该字段天然可读。但需**显式接受两个版本号**，不是只认 1.1 |
| 那行 DO NOT CHANGE | `backupRepository.ts:6` 的注释写着「Backup file format — DO NOT CHANGE」。本次**正是要改它**，须连同该注释一起更新，说明 1.0/1.1 的差异与共存策略 |
| 文件体积 | 会变大——`postData` 是**完整 Post**（`postRepository.ts:42` 深拷贝，含 `content`/`mediaList`），故每条墓碑约等于一条动态的体积。可接受，但值得在文案/文档里说明 |
| 校验 | `RECORD_REQUIREMENTS`（`:48`）需为 `deletedPostIds` 增加必填字段校验；`isRead`/`isBookmarked` 的 `0|1` 约束同样适用 |

### 与 P0-1 的顺序

**A 不修 P0-1。** A 只是让备份**忠实搬运**当前（有缺陷的）状态——抑制与快照仍挤在
`deletedPostIds` 一行，「彻底删除」照样会解除黑名单。

正确顺序：

```
A（备份纳入 deletedPostIds，格式 1.1）
   ↓
P0-1（拆表：suppression 只增不减 / recycleSnapshot 可清）
   ↓
备份自然带上「纯抑制」记录，语义闭合
```

若颠倒（先拆表再改备份），中间态会出现「备份字段刚加就要改含义」，且要多做一次格式迁移。

### 开工方式（必守）

**先写故障注入测试证明现状是坏的**：

```
删一条动态 → 导出备份 → 清库 → 导入备份 → 触发同步 → 该动态复活
```

**红了之后再动格式。** 否则「修好了」没有独立证据——这正是本批审计反复点名的
「实现者与测试作者共享同一个错误世界模型」。

- **限速/节奏**：按平台 interleave、记录**完成时间**、平台 `minRequestIntervalMs` 下限只可抬高、
  rate-limit 后跨 MV3 生命周期持久化 cooldown、指数升级、clean request 清 strike。
- **`POPUP` 不再打包全部 adapter**（`SYNC_CHANNEL` 消息）、`utils/http.ts` 归位、
  三个 dead `checkAuthStatus` 清除、host allowlist 真正 single-source、`CreatorsView` 拆分。

---

## 9. 一句话总结

> 当前 Chorus 最该打掉的根，不是函数长，而是
> **数据库允许存在一些从用户语义上互相矛盾、但 TypeScript 和 555 个测试都认为合法的状态。**

审计最后一条建议，我完全同意并作为本批的执行纪律：

> 现在最危险的操作是又让 Agent 做一轮「全面架构升级」。
> **当前仓库需要的是 5～8 个精确的外科手术，不是再造一套 Clean Architecture。**

# 产品决策记录（ADR-lite）

> **这是什么**：本项目已经做过的**产品方向决定**，以及为什么这样选。
> `AGENTS.md` 是**约束**（怎么写代码），这里是**理由**（为什么这样选）。
> 冲突时以本文件的产品决定为准——每项都记了日期、结论与理由。
>
> **用法**：准备提议一个「改进」「小跟进」或「发现的问题」之前，先在这里搜一遍。
> 已经决定过的事重新提出，等于浪费用户的时间。**若新证据确实与某个决定矛盾，
> 说一次、带上证据、然后等**——不要反复提。

## v1.x 架构冻结（2026-09-14）

**决定**：v1.x 期间**不再主动进行泛化重构**。除下面四类外，审计发现、评审建议、
「代码还能更整齐」一律**不进入待办**。

### 只有这四类进入执行队列

```text
1. 已确认真实 bug；
2. 当前用户可观察问题；
3. 平台接口/行为已经变化；
4. 用户明确批准的新功能或重构。
```

**审计发现 ≠ 待办。** 一份审计报告指出 14 个 P2，不构成「修 14 项」的授权——
它只是材料。**动词就是全部授权**（`AGENTS.md` 规则 32）。

### 为什么

2026-09-14 的三份审计（两轮专项 + 一份外部复核）结论一致：**核心数据语义已经闭环，
平台能力边界已经形成**。剩余价值不再来自继续重构，而来自**把「平台坏了以后怎么局部修」
固定下来**（见 [PLATFORMS.md](PLATFORMS.md) §5）。

而每次「顺手再整理一层」的实际代价是可见的：一个发现会引出实现，实现会引出相邻发现，
收尾变成第二期工程——本仓已经历过多次（规则 9 的「规则瘦身」即因前提不成立而改判）。

### 明确冻结的清单

| 冻结项 | 理由 |
|---|---|
| 完整 `MessageMap` 类型协议 | 可判定的一半已完成（`tests/messageRouter.test.ts`）；完整版需要全仓消息重构 |
| 统一 `PlatformDefinition` | 两份清单已由编译器双向兜底；抽象会为不存在的问题加复杂度 |
| 把所有 adapter 拆成 `collector/contract` 目录 | 只有页面驱动平台需要那层；`weibo.ts`/`pixiv.ts` 一个文件就够 |
| **IndexedDB 分页**（队列 #10） | 目前不是用户问题。**触发条件是实测的**：库到数万条 / 冷启动 > 500ms，再启动 |
| 继续拆 `App.vue` / 继续缩 `AGENTS.md`（57KB） | 前者未形成用户问题；后者刚因前提不成立改判过 |
| 提高全仓 coverage 百分比 | 覆盖率不是目标；`optionalHostAccess` 这类**具体缺口**才值得补 |
| 拆 `release-gate.mjs` | 它是门禁脚本，不是产品代码 |

**不要提议**：把上述任一项作为「收尾的一部分」重新提出。

### 已接受的风险：跨 context 的同步竞争（2026-09-14 判定）

**决定**：**不修**。`syncCoordinator` 的同频道 single-flight 只在**一个 JS context 内**成立。
Dashboard 在页面 context 调 `updateChannel`，auto-sync alarm 在 Service Worker context 调，
两者各持一份 `inFlight`，互不可见——手动刷新与 alarm 同时触发时，同一频道可被两路采集。

**为什么接受**：命中需要「手动刷新恰逢 alarm 触发」；后果是**状态竞争**
（`nextCursor` / `status` / `lastSuccessAt` 由后完成者写回，深挖推进过的游标可能被常规同步覆盖），
不是「多请求一次」。概率低、可见性低。

**为什么不是「随手加个 storage lease」**：`read → empty → write` **不是锁**——两个 context
都会读到空，然后都以为拿到了。真要修，至少要同时具备：跨 context 的**原子 claim**、
`ownerId`、`expiresAt`、**owner 校验释放**（否则过期 holder 会删掉新 holder 的锁）、
崩溃/SW 回收后的恢复。用一个更复杂、更难复现的锁 bug 去换一个低概率竞争，是负收益。

**因此本项的状态是「已知并接受」，不是「已解决」。** 任何文档、注释或提交信息都不得写成已解决；
`syncCoordinator.ts` 的头注释、`PROJECT_PROGRESS` 队列 #2 与 `tests/syncCoordinator.test.ts`
的注释均已按此措辞改写。若将来真要修，先按上述清单证明原子性，再动代码。

## 修 bug 的冷启动流程（AI 维护专用）

**决定（2026-09-14）**：修一个 bug 时，**从零开始、只带这份报告**，不加载整套历史上下文。

### 流程

```text
用户：「<平台> 坏了：<现象>」
      ↓
1. 读 docs/PROJECT_PROGRESS_2026-09.md 的「现状速览」+ 队列（知道哪些已修，别重做）
2. 读 AGENTS.md 的规则（全部读，尤其 **10**（误判到底不可恢复）/ **16**（改适配器不改存量行）/
   **21**（未实测的上游假设）/ **32**（动词即授权）。条数以
   `grep -c '^## [0-9]\+\. ' AGENTS.md` 为准，本文件不写死——它只增不减，写死即过期）
3. 读 PLATFORMS.md §5（这类问题先定位在哪一层，谁拥有什么文件）
4. 按 §5.2 的步骤：跑测试 → 抓真实响应 → 与 fixture diff → 只改平台拥有的文件
5. 若判断要碰通用文件，先确认属于 §5.4 的三个合法例外之一，否则停下来问
```

### 关键保证

**只要 `FetchResult` / `Post` 契约没变，修一个平台不需要动主干。**
实测边界见 [PLATFORMS.md](PLATFORMS.md) §5.3 的表；唯一必然的例外是**存量行修复**
（`channelSync.shouldRepairStoredContent` 加一个分支，规则 16）。

**不要**为了修一个平台的解析问题而读完整的审计历史——

- `docs/AGENTS_CASES.md`（案例全集）
- `docs/AUDIT_2026-09-12.md` / `docs/REVIEW_2026-09.md`
- `docs/archive/`

那些是**证据与历史**，不是约束。**冲突时以源码与 `ARCHITECTURE.md` 的当前状态为准。**

### 不要做的事

- 不要因为「看到了别的问题」顺手修——**报告，不修**（规则 32）。
- 不要新增抽象来「顺便解决」刚发现的耦合。
- 不要为了「有测试」而写测试；为这个 bug 的真实形态写一条，够用。
- **不要开新一轮全面审计**，除非用户点名。

## 记录格式

新增条目时保持同样的三段：**决定（日期 + 一句话结论）** / **理由** / **不要提议什么**。
决定写成结论句，不写对话记录——记的是**决定了什么**与**为什么**，不是谁在什么时候说了哪句话。
